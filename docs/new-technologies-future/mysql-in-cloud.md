# MySQL在云环境中的应用

如今大多数 MySQL 部署都运行在云上：既可以是云主机上的自建实例，也可以是云厂商的托管数据库服务（RDS 类）。本章梳理云上使用 MySQL 的典型形态、托管服务提供的核心能力、迁移与运维要点。

## 1. 云上部署的几种形态

- **自建（Self-managed）**：在云主机（ECS、CVM、EC2 等）上自行安装 MySQL，完全掌控版本与参数，但备份、高可用、监控都要自己负责；
- **托管数据库服务（Managed）**：云厂商提供的 MySQL 兼容服务，如 AWS RDS for MySQL、Azure Database for MySQL、Google Cloud SQL for MySQL、阿里云 RDS for MySQL、腾讯云 TencentDB for MySQL 等，自动化处理备份、补丁、监控与主从切换；
- **云原生增强型**：厂商在 MySQL 之上的自行开发改造，例如 AWS Aurora（存算分离、日志即数据库）、阿里云 PolarDB、腾讯云 TDSQL-C，以及 Oracle 的 MySQL HeatWave（在 MySQL 之上叠加列式内存分析与机器学习能力）；
- **分布式/分片中间层**：Vitess（常部署在 Kubernetes 上）、各类分库分表中间件，用于在云上实现水平扩展。

## 2. 托管服务通常提供的能力

选择托管服务后，大部分运维工作由云平台承担：

- **自动备份与 PITR（Point-in-Time Recovery）**：每日全量备份 + binlog，可恢复到任意时间点；
- **高可用与只读副本**：主备双节点自动故障切换（通常基于半同步复制或类 Aurora 的共享存储），可加多个只读副本分担读压力；
- **监控与告警**：CPU、内存、IOPS、连接数、慢查询、主从延迟等指标的采集与告警；
- **参数模板与安全**：参数组（部分参数可在线修改）、白名单/安全组、TLS 加密传输、静态加密（KMS）、审计日志；
- **弹性与维护窗口**：升降配、存储自动扩容、小版本自动升级（大版本通常需要手动确认）。

需要注意的限制：

- 通常**没有超级权限（SUPER）**，某些全局参数、`LOAD DATA LOCAL INFILE`、UDF、事件调度等能力受限；
- 不能直接访问底层文件系统，因此 **XtraBackup 生成的物理备份一般不能直接恢复到 RDS**，迁移入云多以逻辑备份（mysqldump、MySQL Shell dump）或厂商的导入工具为主；
- 部分插件不可用，组复制/InnoDB Cluster 通常由厂商方案替代（如 RDS 的多可用区部署）。

## 3. 迁移方案

| 方式 | 适用场景 | 说明 |
| ---- | -------- | ---- |
| 逻辑备份导入 | 数据量不大、允许较长停机 | `mysqldump` / `mysqlsh util.dumpInstance()` + `util.loadDump()`，注意字符集与 `sql_mode` |
| 物理备份 | 自建到自建、同构迁移 | XtraBackup 全量 + binlog 增量，速度快，但一般不能直接恢复到托管服务 |
| 主从复制迁移 | 要求不停机切换 | 源库作主，云上实例作从库，追平延迟后切换写入端；推荐开启 GTID |
| 数据同步服务（阿里云 DTS、AWS DMS 等） | 异构或跨云迁移、持续同步 | 支持全量 + 增量，可做结构迁移与双向同步 |
| 混合架构 | 分阶段上云 | 读写分离过渡：先只读副本在云上，验证后再切换写入端 |

迁移前建议核对：字符集（`utf8mb3` → `utf8mb4`）、时区、`sql_mode`、默认认证插件（`caching_sha2_password`）、已废弃变量（如 `query_cache_size` 在 8.0 会直接导致启动失败）、以及应用连接串与连接池配置。

## 4. 云上性能与成本

- **实例规格**：先看 IOPS 与网络吞吐，MySQL 的瓶颈常在存储而不是 CPU；SSD/NVMe 云盘与本地盘的差异会直接体现在 `innodb_io_capacity` 的设定上；
- **参数调优**：托管服务默认参数偏保守，`innodb_buffer_pool_size`、`max_connections`、`innodb_redo_log_capacity`、慢查询日志阈值等仍需按业务调整（部分参数需要重启或使用参数组）；
- **只读副本与读写分离**：把报表、后台查询分流到只读副本；使用 ProxySQL、RDS Proxy 或应用侧的读写分离中间件；
- **Serverless 与按量计费**：部分厂商提供 Serverless 形态（按 ACU/CPU 计费、自动伸缩），适合访问量波动大的业务；持续高负载场景按包年包月更划算；
- **备份与快照成本**：快照、binlog、跨区域复制都会产生存储费用，需要设置保留策略。

## 5. 云上高可用实践

1. **多可用区部署**：主备跨 AZ，自动故障切换，是最基础的高可用保障；
2. **只读副本异地容灾**：跨区域只读副本可在区域级故障时提升为主库（RPO 通常以分钟计）；
3. **监控复制延迟**：`SHOW REPLICA STATUS` 中的 `Seconds_Behind_Source` 与云平台提供的主从延迟指标都要关注；
4. **定期演练**：备份恢复演练、主从切换演练，确认 RTO/RPO 满足业务要求；
5. **权限最小化**：应用账号只授予必要权限，禁用公网访问，开启 TLS 与审计日志。

## 总结

云上使用 MySQL 的核心变化是“运维责任的划分”：托管服务把备份、高可用、监控等交给云平台，而架构设计、参数调优、慢查询治理、迁移与成本控制仍然是使用者的责任。理解托管服务的限制（无 SUPER 权限、不支持直接恢复物理备份、插件受限）并在方案设计时提前规避，是云上平稳运行 MySQL 的关键。
